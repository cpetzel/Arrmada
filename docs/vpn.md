# Downloading through a VPN (Gluetun)

Arrmada has no VPN built in, and won't get one. If you want torrent traffic to leave through
a VPN, run [Gluetun](https://github.com/qdm12/gluetun) beside it and put qBittorrent in
Gluetun's network. This page shows the way that fits Arrmada best.

> This isn't something Arrmada tests or officially supports: it's ordinary Docker, and
> nothing in Arrmada changes for it. Gluetun's own settings (your provider, keys, port
> forwarding) are covered in [Gluetun's wiki](https://github.com/qdm12/gluetun-wiki), not
> here.

## What goes behind the VPN

**Only qBittorrent.** Arrmada itself, FlareSolverr, Prowlarr and SABnzbd stay on your normal
connection.

- **Not Arrmada.** Behind Gluetun, everything Arrmada does goes through the tunnel or stops
  with it: Plex and Jellyfin (on your LAN, which Gluetun blocks unless you open it), TMDB and
  the other metadata sources (some refuse or rate-limit VPN addresses), alerts, the update
  check, and the web page itself, which your reverse proxy and your LAN would then have to
  reach through Gluetun. And when the VPN drops, Gluetun's kill switch cuts off everything
  Arrmada fetches (metadata, Plex, alerts), not just downloads; only its page stays up.
- **Not FlareSolverr.** For TorrentLeech, Arrmada asks FlareSolverr to get past Cloudflare
  once, then signs in and searches itself, carrying the clearance FlareSolverr got.
  Cloudflare ties that clearance to the address it was solved from, so it only works while
  FlareSolverr and Arrmada go out from the same address. Behind Gluetun, TorrentLeech fails
  with Cloudflare errors. (Prowlarr works the same way with FlareSolverr. 1337x and TheXEM
  fetch whole pages through FlareSolverr, so they'd work either way.)

So searches and Arrmada's own traffic use your normal connection; the peers, trackers and
downloads qBittorrent talks to see the VPN's address.

## The Compose install

Add Gluetun to `docker-compose.override.yml` in Arrmada's folder. Compose merges that file
with `docker-compose.yml`, `update.sh` never touches it, and `.gitignore` keeps it out of
git, so it survives updates. Without the installer
([plain Compose](install.md#docker-compose-without-the-installer)), the same file next to
your `docker-compose.yml` works the same way.

**If the installer already wrote one** (its first line is `# Auto-generated by install.sh`,
because you gave it a media folder), add the lines below to it instead of replacing it: its
`/storage` mounts are what let imports hardlink. Then delete that first line. With it there,
a later `install.sh --media` rewrites the file and drops Gluetun; without it, the installer
leaves the file alone and you change the mounts by hand.

```yaml
services:
  gluetun:
    image: qmcgaw/gluetun:v3
    container_name: Arrmada-gluetun
    cap_add: [NET_ADMIN]
    devices: [/dev/net/tun:/dev/net/tun]
    environment:
      TZ: "${TZ:-Etc/UTC}"
      # Your provider's settings, from Gluetun's wiki. For example (Mullvad has no port
      # forwarding since 2023; see "The torrent port" below):
      VPN_SERVICE_PROVIDER: "mullvad"
      VPN_TYPE: "wireguard"
      WIREGUARD_PRIVATE_KEY: "${VPN_WIREGUARD_PRIVATE_KEY}"   # in .env
      WIREGUARD_ADDRESSES: "${VPN_WIREGUARD_ADDRESSES}"
      SERVER_COUNTRIES: "Netherlands"
    ports:
      # qBittorrent's own page, moved here from qBittorrent: same .env settings as before.
      - "${ARRMADA_QBIT_WEBUI_BIND:-127.0.0.1}:${ARRMADA_QBIT_WEBUI_PORT:-8080}:8080"
    networks:
      default:
        # Arrmada keeps reaching qBittorrent by the name it always has.
        aliases: [arrmada-qbittorrent]
    restart: unless-stopped

  arrmada-qbittorrent:
    network_mode: "service:gluetun"
    # A container in another's network can't publish ports of its own.
    ports: !reset []
    depends_on:
      gluetun:
        condition: service_started
```

Then, in Arrmada's folder:

```sh
docker compose up -d
```

(`update.sh` only restarts Arrmada, so it won't move qBittorrent.) `ports: !reset []` needs
Docker Compose 2.24 or newer (`docker compose version`).

### Why it's set up like this

- **The alias.** qBittorrent no longer has an address of its own; it answers on Gluetun's.
  The alias gives Gluetun the name `arrmada-qbittorrent`, so the qBittorrent card in
  **Settings → Connections** stays as it is (`http://arrmada-qbittorrent:8080`) and nothing
  in Arrmada needs changing. Without it the name stops resolving and Arrmada can't reach
  qBittorrent. Don't switch Arrmada to Gluetun's name instead (`ARRMADA_QBITTORRENT_URL:
  http://gluetun:8080`): Arrmada only manages the login of the qBittorrent at
  `arrmada-qbittorrent`, and treats one at any other address as yours. A new install's
  qBittorrent would then keep its first, login-free access for the Docker network instead of
  getting a password ([qBittorrent's login](configuration.md#qbittorrents-login)).
- **The login keeps working.** Arrmada's requests still come from the Docker network the two
  share, which is what qBittorrent's first config and `update.sh --rollback --with-db` (and
  the [troubleshooting steps](troubleshooting.md#qbittorrent-login)) let in until Arrmada
  gives it a password. A qBittorrent that already has one keeps it: it's in qBittorrent's
  own config volume, which doesn't move. **Show its login** works as before.
- **`service_started`, not `service_healthy`.** Arrmada waits for qBittorrent to start, so
  waiting for the VPN to be up would keep Arrmada down whenever the VPN is. qBittorrent can't
  leak while it waits: Gluetun's firewall blocks everything but the tunnel from the start.
- **Folders don't change.** The override doesn't touch qBittorrent's volumes: it keeps
  `/media` and (with the installer's override) `/storage` at the same paths as Arrmada, so
  imports still hardlink ([Hardlinks](configuration.md#hardlinks)).
- **The Docker network is already open.** Gluetun lets its own Docker network in, so Arrmada
  reaches qBittorrent with nothing set. `FIREWALL_OUTBOUND_SUBNETS` (your LAN, e.g.
  `192.168.1.0/24`) is only for when something in Gluetun's network has to reach a computer
  on your LAN, which qBittorrent doesn't.
- **qBittorrent's page is published by Gluetun now.** After changing `ARRMADA_QBIT_WEBUI_BIND`
  or `ARRMADA_QBIT_WEBUI_PORT`, run `docker compose up -d gluetun` (not
  `docker compose up -d arrmada-qbittorrent`, as the other pages say). If the page still
  doesn't open from another computer with `ARRMADA_QBIT_WEBUI_BIND=0.0.0.0`, that's Gluetun's
  firewall: see its wiki.

### The torrent port

The old torrent port lines on qBittorrent are gone (`!reset`): incoming peers now arrive
through the VPN, not your router, so you can drop that port forward.

At every start Arrmada sets qBittorrent's incoming port to `ARRMADA_QBIT_PORT`. Without port
forwarding from your provider (Mullvad, in the example, has none) that's harmless: peers
can't reach you through the VPN, and qBittorrent still downloads, just from fewer of them.
With it, the port is the one your provider gives you, and it may change:

- **A fixed forwarded port:** set `ARRMADA_QBIT_PORT` in `.env` to it, and open it in
  Gluetun's firewall by adding `FIREWALL_VPN_INPUT_PORTS: "<port>"` to Gluetun's
  `environment`. Then `docker compose up -d`.
- **One that changes** (Gluetun's `VPN_PORT_FORWARDING`): tell Arrmada to leave the port
  alone, and keep it current in qBittorrent yourself or with Gluetun's port forwarding
  command (Gluetun opens a port it forwards itself). Add this to the override:

  ```yaml
    arrmada-app:
      environment:
        ARRMADA_QBIT_PORT: "0"   # 0 = don't set qBittorrent's incoming port
  ```

### Living with it

- **When Gluetun restarts, restart qBittorrent too** (`docker compose restart
  arrmada-qbittorrent`): a container in another's network loses it when that one restarts.
  `docker compose up -d` after updating Gluetun's image recreates both.
- **When the VPN is down,** torrents stall, but Arrmada can still add them: Gluetun keeps
  letting its Docker network in. **If Gluetun's container stops,** qBittorrent can't be
  reached: Settings → Status shows it, and grabs wait. Arrmada, Discover, Plex and the rest
  carry on either way.
- **Reverse proxies** don't change: they point at Arrmada as before
  ([Reverse proxies and tunnels](configuration.md#reverse-proxies-and-tunnels)). To proxy
  qBittorrent's own page as well, point the proxy at `arrmada-qbittorrent:8080` (Gluetun),
  and pass the `Host` header through: qBittorrent's CSRF protection compares it with the
  page's address and refuses requests where they differ.
- **Keep the localhost login on** in qBittorrent (Arrmada switches it on): anything else
  you put in Gluetun's network shares qBittorrent's `localhost`.
- **Belt and braces:** in qBittorrent, Tools → Options → Advanced → **Network interface**
  `tun0` keeps it from using any other interface, even if Gluetun's firewall were off.

## The Unraid all-in-one container

Don't put the whole container behind Gluetun, for the reasons [above](#what-goes-behind-the-vpn).
Switch off the built-in qBittorrent and run your own behind Gluetun instead:

1. Edit Arrmada, switch on **Show more settings**, set **Built-in qBittorrent** to `false`
   and **Apply**. Its torrents and settings stay in appdata. You can remove the two torrent
   port entries ([Using your own download client](unraid.md#using-your-own-download-client-or-flaresolverr)).
   Leave **Built-in FlareSolverr** on: it goes out from Arrmada's address, which is what
   TorrentLeech needs.
2. Run Gluetun and a qBittorrent container in its network, with qBittorrent's web UI port
   published on Gluetun. On qBittorrent, Unraid 6.12 and later offer **Network Type**
   `Container:` with Gluetun's container picked; on older versions, use **Network Type**
   `None` and `--net=container:<Gluetun's container name>` in **Extra Parameters**. A Compose
   stack works too. Give qBittorrent your media share at `/storage`, the same as Arrmada, so
   imports hardlink.
3. In Arrmada, **Settings → Connections → + Add client** → qBittorrent: the server's IP and
   the port Gluetun publishes for its web UI (`http://192.168.1.10:8080`), and qBittorrent's
   username and password.

This is your own client, so Arrmada doesn't manage its login or its incoming port; set
those in qBittorrent.
